## 1. 参照系结论与采纳边界

### 1.1 本地克隆实证（2026-08-29 逐条核验）

| 主张 | 实证内容 | 位置（deepseek-harness/ 下） |
|---|---|---|
| Cordis 是 dsh 全部包的容器底座 | "`@deepseek-ai/cordis` is a peerDependency (+ dev) of every harness package" | AGENTS.md L104 |
| Cordis 以 vendor+重挂牌方式固化引用 | `vendor/` 下 cordis、cosmokit、loader、hmr、timer、logger-console、schemastery 等，经 `scripts/rescope-vendor.ts` 统一重挂 `@deepseek-ai` scope（动机：peer dep 随包发布，避免占用上游包名） | vendor/、docs/rescope.md |
| 插件声明式注入模式 | `export const inject = ['agents', 'sessions', 'sessionPersistence']` | docs/cookbook/extension-cookbook.md L48/L73 |
| agent-spine-demo 属实验性原型，非生产组件 | "experimental/ private prototypes excluded from official releases" | AGENTS.md L49、packages/examples/agent-spine-demo |
| 预发布版本线（破坏性变更风险成立） | dsh-root **v0.1.2-alpha.1**（MIT） | package.json、LICENSE |
| 底座设施独立成包的分组旁证 | settings / storage / guard / hooks / **runtime-diagnostics** / bundle / boot 等能力族分组，与本项目 config / save / control / diag / bundle 一一对应 | packages/ 分组（packages/README.md） |

### 1.2 Cordis/dsh 模式中我们采纳什么（模式级）

| Cordis/dsh 概念 | 我们的对应物 | 来源验证 |
|---|---|---|
| Context 作用域树（子作用域可整体挂载/卸载插件） | Kernel 根 Context + Scope 子树（赛季包/A-B/调试） | `@cordis/core` |
| 服务注入（插件声明 `inject`，容器按声明解析） | ServiceDep 声明 + 拓扑启动 | `@cordis/core`、dsh extension cookbook 的 `inject: ['agents','sessions']` 映射法 |
| 类型化事件总线 | 三分类事件词汇表（Domain/Control/Diag） | `@cordis/core` |
| 生命周期 dispose（逆序拆卸、监听回收） | 七相生命周期 + drain + 泄漏检测 | dsh 的 `AgentHandle.dispose()` 契约 |
| Bundle 组合定义宿主差异（dsh-base 共享核心 / dsh-headless 无宿主一次性运行） | clientBundle / headlessBundle / cloudBundle / devBundle | dsh npm 包分层 |
| 基础框架层独立成包、业务只组合不复制 | `@rn/kernel` 单一薄内核包 | dsh 官方建议的 `@company/agent-kernel` 薄适配层思路 |

### 1.3 我们不采纳什么（包级，ADR-11）

1. **不引入 `@deepseek-ai/*` 运行时依赖**：预发布版本线（本地实证 dsh-root v0.1.2-alpha.1，官方标记破坏性变更风险）；且 dsh 包群面向 LLM Agent（session/llm/tools/acp/subagent 等），与游戏无关层占多数。
2. **不引入 `cordisjs/cordis`**：官方声明 API 未稳定（7.8k star 但非 1.0）；其 loader/hmr 能力在微信小游戏环境不可用（禁止动态代码加载）。
3. **决策**：自研 `@rn/kernel` 薄内核（目标 ≤30KB，零游戏知识），**接口形状对标 Cordis**（Context/插件声明/注入/事件/生命周期），保持未来可整体替换；同时把 Cordis 的 loader/hmr 明确排除出范围（对应 FR-B6 平台约束）。

### 1.4 内核设计不得违反的 v1.0 冻结项

确定性禁用清单（逻辑层无墙钟/随机/超越函数）、效果命令模式（唯一状态变更点 `applyEffects`）、逻辑包零平台依赖、M0 数值锚点。诊断与控制面在逻辑层零副作用（NFR-4）。

## 2. 内核模型（@rn/kernel）

### 2.1 核心概念与插件定义形状

```
Kernel（根 Context）
├── Service 注册表        类型化键 → 唯一提供者
├── EventHub              三分类类型化事件（Domain/Control/Diag）
├── Scope 子树            可整体挂载/卸载的插件作用域
└── 生命周期引擎          七相状态机（§2.2）
```

```ts
// 插件声明形状（设计草图）
interface PluginDeclaration {
  name: string                      // 'rn.director'
  version: string
  hotplug: 'core' | 'standard' | 'removable' | 'scope'
  depends: ServiceDep[]             // [{ service:'rn.save', optional:false }, ...]
  provides: ServiceKey[]            // 必须在 provides 列出的服务上注册实现
  consumes: Tag[]                   // 事件词汇表内
  produces: Tag[]
  configSchema: JsonSchema          // 启动期校验，非法即 fail-fast
  hooks: {
    setup(ctx: Context): void       // 同步装配：注册服务、订阅事件
    start(ctx: Context): Promise    // 可异步：平台能力、资源加载
    drain(ctx: Context): Promise    // 停用前：状态经 EffectOp 落盘、收尾异步
    stop(ctx: Context): void        // 停止对外服务
    dispose(ctx: Context): void     // 释放监听/定时器（内核计数校验）
  }
  health(): HealthReport            // ok | degraded | fail + detail
  selfTest?(): SelfTestReport       // 插件范围不变量自检（FR-E4）
}
```

### 2.2 生命周期（七相）

```
REGISTER → RESOLVE → CONFIG → SETUP → START → RUNNING → (STOP → DISPOSE)
                                        ▲                    │
                                        └────── restart ◀────┘（removable/scope 允许）
```

| 相 | 行为 | 失败语义 |
|---|---|---|
| REGISTER | 收集插件声明（Bundle 顺序） | 重名/重复 provide 服务 → 启动失败 |
| RESOLVE | 建依赖图：拓扑排序、环检测、缺失依赖检查 | 缺失依赖 fail-fast；环依赖报错并打印环路路径（AC FR-A2） |
| CONFIG | 加载 JSON 配置 + 本地覆盖，逐插件 schema 校验 | 非法配置 → 该插件不启动（隔离，FR-A3） |
| SETUP | 同步装配（注册服务、订阅事件） | 抛错 → 停用该插件及依赖子树 |
| START | 拓扑序启动（允许异步，如平台登录） | 抛错 → 同上；核心循环不受损（AC FR-A3） |
| RUNNING | 正常运行；接受 mount/unmount/killSwitch | stop 异常 → 内核强制 dispose 并 degraded |
| STOP/DISPOSE | 逆拓扑序 drain→stop→dispose；泄漏计数校验 | dispose 后计数不为零 → Diag 报泄漏（AC FR-B4） |

### 2.3 热插拔分级矩阵（FR-B）

| 分级 | 允许时机 | 状态处理 | 典型插件 |
|---|---|---|---|
| `core` | 仅随进程 | — | kernel、diag、config、control、core-loop、formula、save、systems |
| `standard` | 启动期裁剪（Bundle+配置） | 不参与运行时启停 | battle、stabilizer、observability、director* |
| `removable` | 运行时 stop/start | stop 前必须 drain（状态经 EffectOp 落盘），重挂从 GameState 重建 | ads、iap、cloud、devtools |
| `scope` | 作用域挂载/卸载 | 同 removable，且挂在子 Context | 赛季内容包、A/B 变体、调试工具包 |

\* director 归 standard：内容热更走 `event_lib` JSON（数据级），引擎不卸载。

**关键平台事实**（FR-B6）：微信小游戏禁止远程代码加载，热插拔 = **预置插件的运行时启停 + 内容数据热更（config/event_lib/monster JSON 走远程配置通道）**。赛季新内容 = 新数据包 + 既有 scope 插件参数化，而不是下载新 JS（ADR-16）。

### 2.4 全局控制面（FR-C）

- **ConfigService**（kernel 基座提供）：本地 JSON（`config/*.json`）+ 远程覆盖层（版本化、带版本号回滚；MVP 仅本地，M3 开远程通道）。
- **ControlService**（`rn.control` 插件提供）：feature flags、kill switch、维护模式、模拟控制（timeScale/pause/step，仅 debug 构建注册）。所有变更经单一通道应用并广播 `ControlEvent`，全部留痕（FR-C4）。
- **kill switch 流程**：`requestStop(name)` → `drain()`（状态落盘）→ `stop()` → 该插件消费方收到降级事件（如 ads 停用 → 收租页隐藏 ×2 按钮）→ health 变 degraded → Diag 记 ControlEvent。**保障（FR-C2）**：主循环/结算/存档不感知。

### 2.5 Bundle 组合（FR-G1）

| Bundle | 组成 | 宿主 |
|---|---|---|
| `gameCoreBundle` | kernel+diag+config+control+core-loop+formula+save+systems+battle+director+stabilizer+observability | 一切宿主的公共底座 |
| `clientBundle` | gameCoreBundle + ads + iap + cloud | Cocos（微信/抖音/H5） |
| `headlessBundle` | gameCoreBundle（ads/iap/cloud 以 stub 配置缺席） | 模拟器/CI/复算 |
| `cloudFnBundle` | gameCoreBundle 的只读子集（formula+systems 重放 + diag） | 云函数抽样复算 |
| `devBundle` | clientBundle + devtools + 调试 scope | 开发/内测构建 |

## 4. 依赖图与解耦规则（FR-D）

### 4.1 分层图（服务依赖方向 →）

```
 L0  kernel(生命周期/EventHub)      config(ConfigService)
 L1  diag(Logger/Trace/Metrics/Audit/Health)          ← 依赖 L0
 L2  control(ControlService)        formula(查表API)    ← 依赖 L0/L1
 L3  save(Persistence)  core-loop(PhaseMachine/Rng/Cmd)  ← 依赖 L1/L2
 L4  systems(GameState/applyEffects)                    ← 依赖 L2/L3
 L5  battle   director   stabilizer(只读)               ← 依赖 L4/L2/L1
 L6  observability   ads/iap/cloud   devtools           ← 依赖 L1/L2（经事件消费业务流）
```

### 4.2 边清单（服务依赖，机器可读导出的核心）

```
diag→config→kernel；control→(config,diag)；core-loop→(save,diag,config)；formula→(config,kernel)
systems→(formula,save,diag)；battle→(systems,formula,diag)；director→(systems,formula,diag)
stabilizer→(systems只读,formula,diag)；observability→(diag,config)；ads/iap/cloud→(control,diag)
devtools→(control,diag)
```

### 4.3 事件反通道（避免服务环）

服务依赖严格单向；**回路只允许用事件**：director 产出 `night/plan` → battle 消费；battle 产出 `battle/result` → systems 执行死伤 EffectOps → 广播 `econ/changed` → stabilizer/observability 消费。环路由事件单向流打断，CI 校验服务边无环（AC FR-D3）。

### 4.4 解耦硬规则

① 服务只经注入（CI 禁止插件间深路径 import）；② 状态变更只经 `EffectExecutor`（v1.0 D4 延续，内核不提供其他通道）；③ 事件词汇表外 tag 报错；④ stabilizer 对 systems 只读（类型层面只暴露读接口）。

## 5. 全局日志与诊断体系（FR-E）

### 5.1 分层：基础设施诊断 vs 业务可观测（ADR-13）

```
@rn/diag（底盘，内核级）      Logger / Trace / Metrics / Audit / Health
        ▲ 只被消费
@rn/observability（业务层）   DomainEvent 遥测、M0 曲线带异常检测、快照导出、(M4)经济账本
```

diag 不懂游戏；observability 懂业务但把"怎么记、怎么追"外包给 diag。两者都产出诊断流，但通道不同（`diag/*` vs `obs/*`）。

### 5.2 Logger（FR-E1/E3）

- 记录结构：`{logicalDay, wallTs, level, channel(=插件名), traceId, spanId, msg, data}`。logicalDay 由内核信封注入，插件逻辑层禁止自取时间。
- 级别策略：fatal(坏档/复算失败)/error(功能失败)/warn(降级/调制)/info(业务关键节点)/debug/dev。
- 采样：战斗帧级日志 1/60 抽样；结算/事件链不采样。
- Sink：① 内存环形缓冲（常开，512 条，保底可导出）② dev console（按通道过滤/调级）③ 微信 logManager（仅 error+ 与异常触发上传）④ headless stdout。量预算见 NFR-2。

### 5.3 Trace（FR-E2）

四类标准 span：`dawn-settle`、`battle-session`、`event-chain`（一个事件的选项→EffectOps→结算）、`save`。traceId 随事件信封与 EffectOp 自动透传（内核信封实现，插件零成本）；与 BattleSession 结算哈希同源，**反作弊复算问题与玩家客服问题用同一个 traceId 串联**。

### 5.4 Metrics

每插件自注册 counters/gauges（如 director：事件触发数/保底命中数；battle：夜战胜率/平均死伤；ads：填充/观看）；平台指标（fps/frameTime/memory）由 client 宿主适配层喂入。快照随诊断包导出。

### 5.5 Health 与 SelfTest（分模块诊断，FR-E4）

| 插件 | health 判定 | selfTest 套件 |
|---|---|---|
| systems | 状态树不变量最近一次校验结果 | 全量不变量（金币≥0、人口≤双上限、存档往返） |
| formula | 配置 schema 校验 + 锚点抽查 | D1 租金 1000±5%、r(7)=1.02±0.05 抽查（M0 锚点带） |
| director | 事件库可触发率/保底命中 | event_lib schema + 30 天频控预算模拟 |
| battle | 最近会话重放哈希一致 | 抽样重放近 N 场 |
| save | 最近迁移/往返结果 | 版本迁移 dry-run |
| stabilizer | 是否处于调制态（degraded 语义=主动降级而非故障） | 调制限幅 ±10% 校验 |
| ads/iap/cloud | 平台可用性探测 | 回调签名抽验 |

### 5.6 Audit（审核，FR-E5）

三类审计源，统一环形存储（上限另计，随诊断包导出）：

1. **状态变更审计**：`applyEffects` 挂钩自动记录 `{traceId, sourcePlugin, opsSummary, stateHashBefore, stateHashAfter}`——复用 v1.0 反作弊证据链，一套实现两用（ADR-14）。
2. **控制面审计**：flags/killSwitch/配置变更（操作者/前后值）。
3. **配置变更审计**：远程配置版本切换记录。

### 5.7 诊断工作台与一键导出（FR-E6/E7）

- **dev console**（devBundle，真机可开）：插件表（状态/分级/健康/启停按钮）、日志按通道过滤调级、时间控制（pause/step/timeScale）、selfTest 触发、审计查看、诊断包导出。
- **诊断包结构**：日志环 + 指标快照 + 全插件健康 + 近期审计 + 配置快照（脱敏，剔除支付与账号字段）+ 存档版本与状态哈希。≤200KB（NFR-2），经微信客服/反馈通道回收。
- **headless**：`diagnose --save/--days` 输出同构报告（stdout/JSON），CI 中作为失败附件。

### 5.8 与全局控制联动

killSwitch/配置切换/插件故障 → Diag 记 `ctrl/*` 与 `diag/health` 事件 → 触发时点前后的日志环加标记 → 诊断包自动高亮"事件前后 5 分钟"片段。

## 7. ADR 增补（D11–D16，接 v1.0 §二）

| ADR | 决策 | 理由摘要 |
|---|---|---|
| D11 | 自研 `@rn/kernel` 薄内核，模式对标 Cordis；不引入 `@deepseek-ai/*`（0.x rc、LLM 导向）与 `cordisjs/cordis`（API 未稳定） | 0.x 破坏性风险、微信宿主兼容可控、插件规模 ~15 不需要其全部通用性；接口形状一致保留替换权 |
| D12 | 插件四分级 core/standard/removable/scope，注册时强制声明 | 热插拔边界显式化（FR-B1），评审有据 |
| D13 | 诊断基础设施（diag）与业务可观测（observability）分离 | 底盘不懂游戏、业务不重复造日志；两套通道职责清晰 |
| D14 | 状态变更审计挂在 `applyEffects` 钩子上，与反作弊证据链同源复用 | 单一状态变更点已在 v1.0 冻结，审计零额外通道 |
| D15 | 配置与开关统一走 ControlService 单一通道；远程覆盖 M3 开启 | 防"各插件自行拉远程"失控；MVP 本地先行 |
| D16 | 热插拔 = 预置插件运行时启停 + 数据级热更；排除远程代码加载 | 微信小游戏平台约束（FR-B6）；赛季内容=数据包+scope 参数化 |

## 8. 失败模式与降级总表

| 失败 | 内核行为 | 玩家感知 |
|---|---|---|
| 平台插件 start 失败（登录/广告位拉不起） | 插件 degraded，主循环继续 | 无广告奖励入口，可完整游玩 |
| battle 内部异常 | 会话强制关闭，按"惨胜"带兜底结算并记 error | 当夜少死不不少死（偏玩家有利），次日正常 |
| director 事件库不可用 | 保底池 / 跳过事件槽 | 少一个事件，节奏不变 |
| 存档校验失败 | 回退上一检查点 + fail 诊断上报 | 回到当天开始 |
| 内核级故障 | 进程重启 → 最近检查点恢复 | 重启闪退一次，进度回当日检查点 |
| 远程配置非法版本 | 版本校验失败 → 保持当前版本 + 告警 | 无感 |

## 11. 风险

| 风险 | 缓解 |
|---|---|
| 内核过度通用化，重蹈底座体量错配 | 目标 ≤30KB、零游戏知识红线；不做 loader/hmr/动态作用域 |
| 热插拔把"可停"做成了"可坏" | 四分级 + drain 契约 + kill switch 存活测试（AC FR-B3）为发版门槛 |
| 日志/审计侵入逻辑层破坏确定性 | 信封注入（逻辑层零取时取随机）+ CI 同 seed 双跑含 diag 态 |
| diag 与 observability 边界漂移 | ADR-13：diag 零游戏知识；业务语义只进 observability |
| 控制面被滥用（误 kill core） | core 分级不可 kill；控制面全留痕 + M3 起远程操作双人复核流程 |
