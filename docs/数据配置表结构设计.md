# 数据配置表结构设计（config 六张表 schema v1.0）

> 定位：统一定义 `config/` 下六张 JSON 数据表的字段、约束、校验规则与维护职责。M0 档 §11 提出的"四张表"由此扩展为六张（补 `event_lib`、`building_def`），**本文档为六张表的唯一权威定义**。
> 性质：数据结构设计（schema），不含实现。消费方：`@rn/formula`、`@rn/systems`、`@rn/director`、`@rn/observability`、headless 模拟器、云函数复算。

---

## 1. 通用规则与管线

### 1.1 Excel → JSON → 双端

```
Excel 工作簿（每表一个 sheet）
  → 导出脚本（TS，唯一导出口）：schema 校验 + 锚点断言 → config/*.json
  → CI（GitHub Actions）：schema 校验 + M0 契约回归（headless verify）
  → 消费：客户端 / 云函数 / headless 同读一份
```

### 1.2 通用约束

| 规则 | 内容 |
|---|---|
| 版本 | 每表带 `version`（int 递增）+ `sourceDoc`（来源文档名），破坏性字段变更必须递增并走 ADR |
| 校验 | 启动期 schema 校验 fail-fast（v1.0 §5.2 失败模式），禁止静默缺省值 |
| 数值 | 金币/资源一律整数；比率字段两位小数；枚举字段引用必须在白名单内闭合 |
| 热更 | M1–M2 仅本地打包；M3 起支持远程覆盖层（`local < remote`，版本号可回滚，走 ControlService 单一通道，ADR-15） |
| 维护职责 | `day_curve/constants/monster/iap_sku`＝数值策划（来源 M0 档）；`event_lib`＝文案策划（来源 M0 事件库档）；`building_def`＝系统策划（来源设计方案 4.1） |

## 2. day_curve.json（主曲线表，M0 §5 主表的运行时形态）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `day` | int | 0–31 行连续 | 游戏日 |
| `population` | int | 3–30 | 基准人口（食堂/房间双上限内） |
| `q` | float(2) | ≥0.9 | 品质结构系数 |
| `u` | float(2) | ≥1.0 | 户均升级系数 |
| `income` | int | — | 日租金基准（F2P） |
| `hp` | int | — | 单怪基准 HP（含血月 J） |
| `routes` | int | 1–6 | 进攻路数 W |
| `threat` | int | =hp×routes | 夜晚总威胁 |
| `rTarget` | float(2) | 0.95–1.45 | 防线比值目标 r |
| `fReq` | int | =rTarget×threat | 战力需求 |
| `deaths` | int | 0–1/日 | 基准死亡 |
| `ads` | int | 0–6 | 基准广告次数 |
| `milestone` | string | 可空 | 里程碑/付费点标注 |

**校验断言**（进 CI）：恰 31 行；`income ≈ population×CFG_R0×q×u`（±0.5%）；`hp(非血月日) = hp(前日)×CFG_G_T`（±0.5%）；`fReq = rTarget×threat`（±1）；血月行 `{7,14,21,28}` 的 `hp` 含 ×CFG_J_BM。

## 3. constants.json（常量表，M0 §2 的运行时形态）

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | string | `CFG_*` 命名（与 M0 §2 同名），非法 key 拒绝导出 |
| `value` | number | 当前值 |
| `min` / `max` | number | 安全区间（M0 §2"建议区间"），导出越界即失败 |
| `desc` | string | 作用说明 |
| `sourceDoc` | string | 来源章节 |

**首版必含键**：`CFG_R0=100、CFG_G_U=1.055、CFG_G_T=1.15、CFG_HP0=100、CFG_J_BM=1.6、CFG_K_POWER=2.6、CFG_ECPM=45`；恐慌系（v1.0 §5.3）`PANIC_MAX=100、PANIC_ESCAPE_AT=70、PANIC_ESCAPE_P=0.15、PANIC_DECAY=10、PANIC_PROP_FLOOR=5、PANIC_MEAN_PENALTY_AT=50、PANIC_MEAN_PENALTY=0.9、TUTORIAL_PANIC_CAP=30`；护栏系 `GUARD_DEATH_DAY=4、GUARD_DEATH_30D=6`；稳定器系 `STAB_J_ADJUST_MIN=0.9、STAB_J_ADJUST_MAX=1.1、STAB_OVERFLOW_DAMPING`。**命名红线**：代码逻辑禁止出现本表之外的魔法数字（v1.0 §11）。

## 4. monster.json（怪物变种表，设计方案 4.5 进化树）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` / `tier` | string / string / enum(`minion`/`elite`/`boss`) | 标识与定位 |
| `unlockDay` | int | 入池日（对齐 day_curve 难度段） |
| `hpMul` | float(2) | 相对 `CFG_HP0` 倍率（强度主干仍走 day_curve，本表只做变种修正） |
| `mechanics` | enum[] | `breakDoor / climbWindow / fly / focusFire / silentCompat` 等，白名单校验 |
| `usableNightMods` | enum[] | 可出现在哪种特殊夜（BLOOD_MOON/SILENT/MIGRATE/普通） |

**首版行**：循声者(minion,D1)、破窗者(minion,D3,breakDoor)、攀楼种(minion,D5,climbWindow)、飞行种(elite,D9,fly)、围攻AI(elite,D12,focusFire)、精英种(elite,D18)、夜王(boss,赛季,day30 预告)。强度以机制复杂度表达，不再叠指数（M0 §4.1 修正的延续）。

## 5. iap_sku.json（商业化 SKU 表，M0 §7.2 结构化）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `type` | string / enum(`firstCharge`/`pack`/`pass`/`monthly`/`gacha`) | SKU 标识 |
| `price` | number(元) | 定价 |
| `contents` | `EffectOp[]`（受护栏校验） | 内含资源/解锁，格式与事件效果同词汇 |
| `valueAnchor` | float | 性价比锚（如月卡 4.7×），供对账 |
| `triggerDay` / `triggerEvent` | int / string | 曝光时点（3/7/14/赛季），对齐 M0 §7.2 |
| `repeatable` | bool | 可复购 |

**校验**：`triggerDay ∈ {3,7,14,28,30,season}` 语义白名单；`firstCharge` 唯一；contents 不得含 KILL_TENANT。

## 6. event_lib.json（事件库，M0 事件文档 50 条的结构化形态）

schema 沿用内核档 §5.4 定义，此处补字段约束与校验：

| 字段 | 约束 |
|---|---|
| `id` | 全局唯一，前缀分组：`evt_tut_*`（教学）/ `evt_*`（抉择）/ `evt_mis_*`（任务）/ `evt_ord_*`（秩序） |
| `type` | enum(`scripted`/`choice`/`mission`) |
| `weight` / `cooldownDays` / `maxPerRun` | 1–100 / 1–14 / 1–5；`scripted` 类型三者忽略（走天数触发） |
| `prereq` | 字段白名单：`dayMin/dayMax/panicMin/panicMax/reputationMin/flags{}` |
| `options[].outcomes[].p` | 同一 outcome 列表合计 =1（±0.001），导出断言 |
| `options[].outcomes[].effects[]` | `EffectOp` 白名单，**禁 KILL_TENANT**；单事件 `ADD_PANIC ≤25`、`ADD_GOLD ≤3000` |
| 库级 | 恰 50 条（8 scripted + 24 choice + 10 mission + 8 ord）；`scripted` 的 `triggerDay` 唯一 |

## 7. building_def.json（建筑与槽位表，设计方案 4.1 结构化）

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | enum | `room`(住户房间) 或公共建筑：`gate/wall/watchtower/broadcast/warehouse/canteen/clinic/hall/workshop` |
| `level` | int | 等级线 |
| `cost` | `{material,gold,...}` | 升级消耗（整数） |
| `slots` | `{tenant?,fort?,post?}` | 槽位授予：房间=tenant×1+fort×2；公共建筑按级给 post/容量 |
| `capacity` | int? | 食堂→人口上限；仓库→资源容量（软卡点，对齐 D3） |
| `unlockDay` / `unlockFloor` | int | 解锁条件 |

**首版关键锚**：食堂 Lv 序列须覆盖 `day_curve.population`（人口上限的约束源）；仓库 Lv2 在 D3 前可达成（软卡点可解）；每层 5 房×6 层=第 1 栋 30 户（D30 满层锚点）。

## 8. 校验与验收汇总

| 校验 | 执行点 | 失败处理 |
|---|---|---|
| 六表 schema 校验 | 导出脚本 + CI + 客户端启动期 | fail-fast，拒绝运行 |
| M0 锚点回归（day_curve/constants） | CI `headless verify` | 阻断合入 |
| event_lib 护栏（p 合计/效果白名单/50 条） | 导出脚本 + CI | 阻断合入 |
| 远程覆盖层合法性（M3+） | ControlService 版本校验 | 保持当前版本 + 告警（内核档 §8） |
